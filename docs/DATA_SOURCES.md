## 3. 分时分钟轴对齐实测规范（极重要）

通过对比腾讯 `day/query` 与东财 `trends2` 的逐分钟真实数据（以 `600519.SH`、`000001.SH` 校验）：

1. **`09:30` 记录的真实语义是开盘集合竞价**：
   - 例：`600519.SH` 2026-11-24 `09:30` 在腾讯与东财均为 `价=1425.00, 量=763手, 额=108,727,500.00元`，精确满足 `763 × 100 × 1425.00 = 108,727,500.00`，开高低收完全相等。
   - 这证明 **`09:30` 这条记录就是 `09:25` 开盘集合竞价的终态结果**；连续竞价第一分钟 `09:30:00–09:30:59` 归属于 **`09:31`** 标签！
2. **连续竞价 240 根分钟线映射约定（与上游 100% 对齐）**：
   - **集合竞价锚点（独立存储 `auction_snapshots`）**：标签 `09:30`（盘中 `09:25–09:29` 由实时快照捕获 `auction_turnover`，收盘/补齐时由分时 `09:30` 节点对应）。
   - **上午连续竞价（`minuteIndex = 0..119`，共 120 根）**：对应上游时间标签 **`09:31` → `0` … `11:30` → `119`**。
     - 其中 `cum_turnover(0)` 包含 `09:30` 开盘竞价 + `09:30–09:31` 第一分钟成交额（与两市快照当日累计口径一致）。
     - 若需单独看第一分钟纯连续竞价增量 `bar_turnover(0)` = `cum_turnover(09:31) - auction_turnover(09:30)`。
   - **午休折叠**：
     - 东财 `trends2` 天然无 `13:00` 节点（共 `1 + 120 + 120 = 241` 条）。
     - 腾讯 `day/query` 包含 **`1300` 节点**（实测数值与 `1130` 完全一致，共 `242` 条），**适配器必须丢弃 `1300`**，防止午休重复计数。
   - **下午连续竞价（`minuteIndex = 120..239`，共 120 根）**：对应上游时间标签 **`13:01` → `120` … `15:00` → `239`**。
   - **盘后固定价格交易过滤（实测陷阱）**：
     - 腾讯 `day/query` 对沪深个股（实测 `600519.SH`、`300750.SZ` 均返回 **267 条**）会返回 `1501`–`1530` 的盘后固定/定价交易数据（如 `600519.SH` `1530` 累计 `62.1506 亿` vs `1500` 收盘 `62.1419 亿`）。
     - **适配器必须硬截断 `HHMM <= 1500`**，仅保留 `0930`（竞价锚点）+ `0931..1130` + `1301..1500`，确保与收盘快照精确一致且每个交易日严格为 `240` 根连续分钟线！

## 4. 各数据源精确契约与字段映射

所有 `MarketDataProvider` 适配器必须在边界层输出统一单位：
- **成交额 (`turnover`)**：人民币 **元**（`number`）
- **成交量 (`volume`)**：**股**（`number`）或按统一约定（建议统一为**股**，或在 `Snapshot` 中明确 `volumeShares`）
- **涨跌幅 (`changePct`)**：百分比数值（如 `1.46` 表示 `+1.46%`）

### 4.1 主公开源：腾讯财经（Tencent）

#### 代码映射规则
- `000001.SH` → `sh000001`；`399106.SZ` → `sz399106`；`600519.SH` → `sh600519`（规则：`${exchange.toLowerCase()}${ticker}`）。

#### A. 批量实时快照
- **URL**：`https://qt.gtimg.cn/q=sh000001,sz399106,sz399001,sz399006,sh000688,sh600519,sz300750`
- **请求头**：`Referer: https://gu.qq.com/`、`User-Agent: Chrome UA`
- **编码**：**GB18030**（使用 `new TextDecoder('gb18030').decode(buf)`）
- **响应格式**：每行 `v_<txCode>="<tilde-separated-fields>";`
- **核心字段映射**（按 `~` 分割，`parts[i]`）：

| 索引 | 含义 | 原始单位/示例 | 标准化换算 |
| --- | --- | --- | --- |
| `1` | 标的名称 | `上证指数` | 原值 |
| `2` | 6位代码 | `000001` | 结合前缀拼为 `000001.SH` |
| `3` | 最新价/点位 | `3548.37` | `Number(parts[3])` |
| `4` | 昨收 | `3538.95` | `Number(parts[4])` |
| `5` | 今开 | `3567.84` | `Number(parts[5])` |
| `6` / `36` | 成交量 | **手**（`493526296`） | 转为股：`× 100` |
| `30` | 行情时间戳 | `20261124160927` (`yyyyMMddHHmmss`) | 解析为 Asia/Shanghai 时间 |
| `31` | 涨跌额 | `9.42` | `Number(parts[31])` |
| `32` | 涨跌幅 | `0.27` (%) | `Number(parts[32])` |
| `33` / `34` | 最高 / 最低 | `3585.22` / `3539.01` | `Number(...)` |
| **`35`** | `最新价/成交量(手)/成交额(元)` | `3548.37/493526296/771861010309` | **首选成交额**：取第三段 `Number(p35[2])`，**系数 `× 1`（精确到元）** |
| `37` | 成交额（万元，取整） | `77186101` | 兜底成交额：`Number(parts[37]) × 10000`（当 `parts[35]` 第三段缺失时使用） |

#### B. 5 日 1 分钟分时基线（今 + 昨 + 前 3 日）
- **URL**：`https://web.ifzq.gtimg.cn/appstock/app/day/query?code=<txCode>`
- **请求头**：`Referer: https://gu.qq.com/`
- **编码**：UTF-8 JSON
- **响应路径**：`json.data[txCode].data` → 数组（按日期倒序，`[0]` 为最新交易日，`[1]` 为上一交易日，共 5 个交易日）
- **单日对象**：`{ date: "20261124", prec: "3538.95", data: ["0930 3567.84 7725349 12728771688.50", ...] }`
- **单行解析**（空格分隔 4 字段）：
  - `[0]`：`HHMM`（如 `0930`、`0931`、`1500`）
  - `[1]`：分钟价/点位（`number`）
  - `[2]`：**累计成交量（手）** → 转为股 `× 100`
  - `[3]`：**累计成交额（元）** → **系数 `× 1`**（无需累加，直接为截至该分钟的当日累计额；单分钟增量 `barTurnover = cumTurnover[i] - cumTurnover[i-1]`）
- **必须执行的清洗规则**：
  - `HHMM === '0930'` → 写入 `auction_snapshots`（`open_price = price`, `auction_turnover = cumTurnover`）
  - `HHMM === '1300'` → **跳过**（午休重复锚点）
  - `HHMM > '1500'` → **丢弃**（过滤沪市盘后固定价格交易）
  - 仅保留 `0931..1130`（`minuteIndex 0..119`）与 `1301..1500`（`minuteIndex 120..239`）。

#### C. 当日分时（轻量单日备选）
- **URL**：`https://web.ifzq.gtimg.cn/appstock/app/minute/query?code=<txCode>`
- **响应路径**：`json.data[txCode].data.data`（格式与 `day/query` 完全一致，延迟 78~147ms）。

#### D. 标的搜索兜底
- **URL**：`https://smartbox.gtimg.cn/s3/?v=2&q=<encodeURIComponent(keyword)>&t=all`
- **编码**：GB18030，响应形如 `v_hint="sz~300750~\u5b81\u5fb7\u65f6\u4ee3~ndsd~GP-A^..."`，以 `^` 分条、`~` 分字段，过滤 `market in ('sh','sz')` 且类型含 `GP-A`（A股）或 `ZS`（指数）。实测延迟 **149ms**。

  - **注意域名**：必须使用 **`push2his.eastmoney.com`**（实测 `push2.eastmoney.com` 即使传 `ndays=2` 也仅返回当日 1 天 241 条；`push2his` 正确返回 2 天共 482 条）。
- **请求头**：`Referer: https://quote.eastmoney.com/`
- **响应路径**：`json.data.trends[]`，每条逗号分隔：
  - `f51`（index 0）：`YYYY-MM-DD HH:mm`
  - `f52..f55`（index 1..4）：开、收（当前价）、高、低（注：历史日开盘价 `f52` 为 `0.00`，请统一用 `f53` 收盘价作为该分钟价格）
  - `f56`（index 5）：**单分钟增量成交量（手）** → 转为股 `× 100`
  - **`f57`（index 6）**：**单分钟增量成交额（元）** → **系数 `× 1`**（需前缀和累加得到 `cum_turnover`，实测 241 条累加与全天快照误差 < 200 元 / 8000 亿）
  - `f58`（index 7）：均价
- **冷启动实测耗时**：串行（间隔 150ms）拉取 8 个标的 2 日完整 1 分钟线，总耗时 **3.26 秒**（单标 56~372ms），全部 8/8 成功。

#### B. 批量快照（降级低频备源，严禁 3s 高频主用）
- **URL**：`https://push2.eastmoney.com/api/qt/ulist.np/get?fltt=2&invt=2&fields=f1,f2,f3,f4,f5,f6,f12,f13,f14,f15,f16,f17,f18,f124&secids=<comma-separated>`
  - 备用分片节点实测可用：`82.push2.eastmoney.com`
- **字段映射**：`f2`=最新价、`f3`=涨跌幅(%)、`f4`=涨跌额、`f5`=成交量(**手**，`× 100` 转股)、**`f6`=成交额(元，`× 1`)**、`f12`=代码、`f13`=市场(`1`=SH,`0`=SZ)、`f14`=名称、`f15..f18`=高/低/开/昨收、`f124`=秒级 Unix 时间戳。
- **实测风险警告**：`push2.eastmoney.com` 对持续高频请求存在服务端主动断连（`UND_ERR_SOCKET`，`bytesRead: 0`），即使加 `Connection: close` 也会被断连。仅在腾讯、新浪同时不可用时低频启用（或切换分片子域并做退避）。

#### C. 搜索联想兜底
- **URL**：`https://searchapi.eastmoney.com/api/suggest/get?input=<encodeURIComponent(keyword)>&type=14&count=10`
- **实测表现**：延迟 **77ms**，返回 JSON `QuotationCodeTable.Data[]`，过滤 `MktNum in ('0','1')`（沪深 A 股/指数），映射为 `${Code}.${MktNum === '1' ? 'SH' : 'SZ'}`。

### 5.2 推荐默认轮询预算与故障转移设计（供 Phase 3 直接落地）

1. **盘中默认快照轮询间隔**：**`3 秒`**（用户可在设置页调整为 `3~15 秒`）。
   - 全部监控标的（5 指数 + 全部自选股）合并为 **1 次批量请求**。
   - 若用户自选股超过 40 只，按每批 ≤ 50 标的拆分（腾讯/新浪单次 URL 均可轻松支持 50+ 标的）。
2. **快照源故障转移链路**：
   - **Primary**：腾讯 `qt.gtimg.cn`
   - **Secondary**：新浪 `hq.sinajs.cn`（连续失败 ≥ 3 次或超时/429/403 时无缝切换；口径与腾讯 100% 一致，无须重拉基线）
   - **Emergency Fallback**：同花顺 Fuyao（仅当腾讯与新浪同时不可用且已配置 API Key 时启用，强制降频至 **≥ 15 秒**，UI 显式提示降级状态；注意 `399006.SZ` 口径差）
   - **退避与自动探测恢复**：失败后执行有界指数退避（`3s → 6s → 12s`，上限 `30s`）；切至备用源后每 5 分钟对主源做 1 次轻量健康探测，恢复后平滑切回。
3. **1 分钟分时基线补齐策略（启动 / 盘前 / 添加新自选股时）**：
   - 先查 SQLite `intraday_bars` 是否已有 `prevTradingDate` 完整 240 根及今日已过分钟。
   - 仅对缺失标的按并发度 `2`（每次间隔 `150ms`）调用 **腾讯 `day/query`** 一次性补齐近 5 日 1 分钟数据；单标失败时自动回退至 **东财 `push2his` `trends2`**（并发度 `1`，间隔 `200ms`）。
   - 盘中正常运行时不再重复拉取 `day/query`，由 3 秒快照在本地聚合生成闭合 1 分钟线落盘，极大降低请求量。
4. **非交易时段**：
   - `11:30–13:00` 午休、`15:01` 盘后与非交易日自动停止 3 秒快照轮询，保留最近交易日完整数据供复盘。

## 6. 零 MSVC 编译 SQLite 方案实测结论

宿主机 Windows 环境无 MSVC（`cl.exe`），拒绝任何需要 `node-gyp` 编译的依赖（如 `better-sqlite3`、`sqlite3`）。

### 6.1 真实 Electron 进程实测结果

在独立临时目录安装 `electron@45.4.1`（零编译报错），通过完整 Electron 主进程（`app.whenReady()`）实测执行 `require('node:sqlite')`：

| 实测项 | 结果 |
| --- | --- |
| Electron 版本 | **`45.4.1`**（win32 x64） |
| 内嵌 Node.js 版本 | **`24.22.3`** |
| 内嵌 Chromium 版本 | `156.0.8078.100` |
| `require('node:sqlite').DatabaseSync` | **原生可用（`true`）**，无 `No such binding: sqlite`，无 `ExperimentalWarning` |
| 内置 SQLite 版本 | **`3.54.1`** |
| `PRAGMA journal_mode = WAL` | **支持（`true`）** |
| 建表 + 事务预处理批量写入 + 关闭重开读回 | **全部通过（`crudPassed: true`）** |
| 是否需要 MSVC / Python / `@electron/rebuild` | **否（完全零原生构建依赖）** |

### 6.2 工程落地定型（供 Phase 1 采用）

- **最终定型**：Phase 1 锁定 **`electron@^45.4.1`**，主进程持久层 `src/main/storage/database.ts` 直接使用 Node.js 内置 **`node:sqlite` (`DatabaseSync`)**，开启 `PRAGMA journal_mode = WAL;` 与 `PRAGMA busy_timeout = 5000;`。
- **单测一致性**：宿主机 Node `v26.7.0` 同样原生内置 `node:sqlite`，因此 `vitest` 可以直接对真实 SQLite（`:memory:` 或临时文件）运行全部持久层与 30 交易日滚动清理测试，零 mock 失真。
- **环境安装提示（重要）**：
  - 本机实测若 npm 配置了 `ignore-scripts` 或直连 GitHub 下载较慢，安装 Electron 时可能跳过/卡住 `install.js` 下载二进制。
  - Phase 1 建议在 `.npmrc` 或安装说明中配置国内镜像 `ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/`（实测约 10 秒完成下载）。
